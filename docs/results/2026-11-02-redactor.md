# Results: the redactor, faster and tolerant of garbled echoes (2026-11-02)

Three changes to `mobiusguard-redact` and how they measured: a keyword prefilter for CPU
cost, patterns that survive the ways models garble a secret they repeat, and a fix for text
held back after a private key. Same evaluation as
[2026-10-27](2026-10-27-baselines.md) (suite `ids_sha256 6db51432…`, 57,064 public prompts
and messages); run on an AWS g6.xlarge (AMD EPYC CPU), Python 3.12.

## Garbled echoes: nothing leaked

The live check ([2026-10-30](2026-10-30-live-check.md)) showed that models do not repeat a
secret exactly. The redactor evaluation now has four garbled families besides the exact
values, each value placed in a real message and streamed in random chunks:

| Family | What the model does | Cases | Leaked | Streamed = one-shot |
|---|---|---:|---:|---:|
| exact | repeats the value as given | 4,800 | 0 | 100% |
| wrapped | backticks, quotes, brackets, bold, trailing punctuation | 4,800 | 0 | 100% |
| longer | a token with 1–4 characters added | 2,400 | 0 | 100% |
| shorter | a token with 1–3 characters dropped | 2,400 | 0 | 100% |
| context | other surroundings: a URL without its host, `redis://:pw@…`, a bare `Bearer`, "secret key" without "AWS" | 600 | 0 | 100% |

*Leaked* means an 8-character piece of the value as written reached the output (pieces
that also occur in the surrounding message are not counted). 3.4% of the garbled cases
were redacted by a gitleaks rule (`generic-api-key`) rather than the curated pattern for
that value, so their label is less specific; at the time of the run that included every
shortened Stripe key, because the curated Stripe pattern still required 24 characters
(fixed afterwards, see the last section).

**These patterns were changed after seeing the garbled results** (decision 0006): a first,
small sample (10 cases per group) leaked AWS key IDs and GitHub, GitLab, Google and Hugging
Face tokens that were a few characters off, bearer tokens without their header or in
quotes, AWS secret keys in brackets or after "secret key", and `redis://:password@host`.
Token patterns now accept a few characters more or less than the exact length, and the
others were widened as described in [decision 0007](../decisions/0007-streaming-redaction-semantics.md).
Their cost on text they were not tuned on:

- **Firing on 57,064 public texts: unchanged.** Every pattern fires on exactly as many
  texts as before the changes (2,435 pattern-text pairs in total), so the wider patterns
  added no new matches there.
- Near misses (a bad check digit, a too-short key) are still not labelled as the pattern,
  except 1 in 200 phone numbers, as before (a flaw in how the test built that case; see the
  last section).

## The keyword prefilter: 3x faster, same output

A gitleaks rule now runs only where one of its keywords is in the text not yet sent, or is
arriving at its end. 177 of the 221 rules use it; 44 always run because their keyword is
not a safe filter for streaming (the reasons are in decision 0007).

Per 4-character chunk, this repository's docs and code (288,727 characters) streamed
through all 245 patterns:

| | P50 | P95 | P99 | Max |
|---|---:|---:|---:|---:|
| with the prefilter | **0.146 ms** | 0.231 ms | **0.404 ms** | 7.8 ms |
| without | 0.437 ms | 0.922 ms | 2.132 ms | 23.0 ms |
| curated patterns only | 0.038 ms | 0.047 ms | 0.053 ms | 0.26 ms |

On all 57,064 public texts, the output with and without the prefilter is identical. That
is a check, not an assumption: one rule (`lob-api-key`, whose match needs "lob" before its
keyword) made the stress tests fail until it was taken out of the prefilter, and the
safety test now checks every rule for that case.

## Text after a private key is no longer held back

Both private-key patterns could run on to a later END line, so after a model printed a key,
the rest of the reply was held back until the 8,192-character limit and then replaced with
`[REDACTED:holdback_overflow]`. The benchmark found it as soon as its input contained a PEM
block (the most text held back reached 8,191 characters). A key now ends at its first END
line, and a key cut off before its END line at the end of a reply (a model reaching its
token limit) is redacted rather than passed on. Delay now: 3 characters held back at P50,
41 at P99, and at most 500, which follows the word `curl` (gitleaks' curl rules look a few
lines ahead).

## Three follow-ups, checked in a targeted run

Made after the run above and measured only where they act, on the same 57,064 public texts
and seed (the next full run, before the release, measures everything again):

- **A shortened Stripe key** is now labelled `stripe_secret_key` (20 characters or more
  instead of 24): 200 of 200, up from 0, none leaked.
- **The curl rules** follow a command onto the next line only after a continuation
  character, so the lines after the word "curl" are no longer held back (a streaming test
  checks it). Firing on the public texts is unchanged for all three patterns (Stripe 0,
  curl header 1, curl user 0); the one curl finding is a real multi-line command.
- **The phone near miss** was the test's own doing: the phrase was put in after the "3." of
  "Python 3.11", or before a line starting "2. ...", so the 7-digit near miss ran on into
  those digits and became a plausible phone number. Phrases now go in at real sentence ends
  and as a line of their own at line breaks: all five near-miss groups are labelled 0 of 200.
